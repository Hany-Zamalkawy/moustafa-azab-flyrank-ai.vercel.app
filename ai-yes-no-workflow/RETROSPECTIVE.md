# Retrospective — a draft for the Week 1 version of me

*Draft based on the project files and work records. Review it, replace any wording that does not match your own experience, and keep the final version between 500 and 800 words before submitting.*

At the beginning of this track, I was focused on making an AI project that could answer a useful question. The work became broader than a single model call. Across El-Mizan and the later workflow projects, the important problem was how to make a result understandable, bounded, and dependable enough that another person could see what happened. The final Branchline project makes that shift visible: a user can edit a decision graph, submit one message, and watch a background workflow follow its YES or NO path.

The project changed as I learned to distinguish a working demo from evidence of a working product. El-Mizan began with a narrow public-service navigation task: guide someone replacing a lost or damaged Egyptian national ID toward the official portal, without pretending to decide eligibility or submit a government form. The source lookup encountered an official portal page that returned an error, so the project records that limitation rather than inventing a procedure. Later, I built an LLM-backed classification API with a schema, timeouts, retries, and tests, then moved slow work behind a `202 Accepted` endpoint and a pollable status route. A report generator added another practical concern: deterministic input data, repeatable output, and an actual downloadable PDF.

Branchline brings those pieces together in a visual form. React Flow shows the graph, an Express API validates it, and Inngest executes each visited decision as a durable step. A strict YES/NO output is intended to keep model decisions usable by code. The interface shows the active node, selected route, and ordered log. The local end-to-end run completed in demo mode: the support question returned YES, then the urgency question returned NO. That confirms the queue, traversal, and status display worked in that run; it does not prove that OpenAI was called or that the model makes accurate decisions. No API key was configured, and no formal v2 evaluation suite was present in the project materials.

One design decision I would carry forward is making the workflow graph explicit and validating it before queueing. A clear graph helps a person inspect what the system might do, while checks for a single start node, valid branch handles, and cycles prevent some malformed jobs from reaching the worker. One limitation I would state plainly is that Branchline stores run status in process memory. A server restart loses those records, so a real deployment needs persistent storage and additional operational monitoring. The demo classifier is another limitation: it is only a predictable way to exercise routing without a provider key.

Three lessons from the track feel transferable. First, constrain model output at the boundary and validate it again in application code; a prompt alone is not a reliable interface. Second, move slow work out of a request, return a job identifier quickly, and design for retries and duplicate delivery. Third, preserve the difference between verified evidence and assumptions. A passing build, a local smoke run, a live provider evaluation, a phone test, and a public deployment are different claims and need different proof.

What changed most in how I work is that I now treat failure paths and evidence as part of the feature. I record which dependency or source failed, what I changed, and what remains unverified. I also prefer to build the smallest end-to-end path before polishing edge cases. Next, I would persist workflow runs, add a measured decision evaluation set with expected YES/NO outcomes, test retry and terminal-failure behavior, and run the actual OpenAI path. Then I would capture the live demonstration, publish the complete package, and ask a reviewer to challenge both the design and the evidence.
